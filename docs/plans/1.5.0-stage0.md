# 1.5.0 stage 0 - 1.4.8 measured on a real model (11 Nov 2026)

How it was measured: the exact request each kind of turn sends (messages + tool schemas, built by the 1.4.7 code at `aab92cd` and by 1.4.8), sent straight to llama-server - no chats saved. Model: Qwen3.5-9B-Abliterated-Claude-4.6-Opus-Reasoning-Distilled-v2 Q4_K_M on the RTX 3060 Ti (8 GB), 48,521-token context, all layers on the GPU. Numbers are llama-server's own timings (`prompt_n`, `prompt_ms`, `cache_n`).

## Found first: the GPU wasn't used at all

- llama-server listed **no GPU** ("Available devices: (none)"): two of NVIDIA's three runtime files were missing and the third was cut short. An update unpacked them while C: was nearly full, and nothing checked the result. Every model ran on the CPU: **4.2 tokens/s**.
- With the runtime restored: 16.0 tokens/s, still low because the model's 65,536-token context didn't fit beside it in 8 GB and overflowed into system RAM.
- With a context that fits (48,521, set by the owner/Diagnostics): **63.2 tokens/s** writing, 99.5 tokens/s reading - 15 times the first number.
- Fixed in 1.4.8: setup checks a CUDA build really sees the GPU (else keeps the old one) and repairs an install that doesn't; it checks free space before downloading; Diagnostics says so when the engine can't use the GPU; new Qwen 3.5 models get a context that fits.

## Tokens the model reads per request (cold, nothing cached)

| Turn | 1.4.7 tokens / time | 1.4.8 tokens / time | Saved |
|---|---|---|---|
| greeting | 2,632 / 1.48 s | 2,377 / 1.02 s | 10% |
| plain question | 2,899 / 1.22 s | 2,597 / 1.12 s | 10% |
| web question | 3,741 / 1.57 s | 2,760 / 1.18 s | 26% |
| picture | 4,842 / 1.98 s | 4,369 / 1.82 s | 10% |
| PC action | 3,957 / 1.64 s | 3,492 / 1.48 s | 12% |
| Roblox action | 5,182 / 2.14 s | 4,737 / 1.96 s | 9% |
| voice question | 3,969 / 1.64 s | 2,883 / 1.23 s | 27% |

The app's own estimate (`tools/prompt_inventory.py`) said up to 44%; the real tokenizer packs the tool schemas tighter, so the real saving is 9-27%. The estimate overstates schema-heavy parts.

## Switching kinds of turn in one chat (cache on)

| Sequence step | 1.4.7 read / reused | 1.4.8 read / reused |
|---|---|---|
| question after a greeting | 648 / 2,251 | 455 / 2,142 |
| web question after a question | **3,741 / 0** (1.58 s) | **899 / 1,861** (0.48 s) |
| question after a web question | **2,899 / 0** (1.27 s) | **736 / 1,861** (0.43 s) |
| voice question after a web question | 684 / 3,285 | 407 / 2,476 |

1.4.7 re-read the whole request each time a question and a web question alternated; 1.4.8 reuses the shared start (item 7), so those switches read about 3-4 times less.
(llama-server also keeps recent prompts in host memory, which is why some later steps in both versions read almost nothing; the two bold rows are the clean comparison.)

## Other measurements

- **App start:** first answer 6.1 s -> 2.4 s after launch (Diagnostics and a process scan now wait 8 s; the first request's imports moved before listening). **Exit:** 22.6 s -> 2.9 s (timers that kept the process alive are background threads now).
- **Long answers:** the reply limit was 2,048 tokens and a cut-off answer simply ended; now 8,192 and a cut-off answer continues where it stopped.
