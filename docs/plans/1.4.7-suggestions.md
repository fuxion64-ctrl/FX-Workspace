# 1.4.7 - suggestions waiting for approval

Found during the reliability pass; not built.

1. **Models whose file is gone still show in the picker.** Your models.ini lists Gemma-4-E4B-Tools, whose file isn't on E: any more, and several mmproj files the router can't open (gemma-4-E2B .mmproj, Ornith-1.5-9B-MTP, gemma-4-12b BF16). Picking one now says plainly that the file is missing, but it would be better to mark them in the model picker ("file missing") and offer to remove the entry or find the file.
2. **Ornith-1.5-35B-A3B needs 17.5 GB of free RAM to load** (load-mode = none reads its experts into RAM). With the PC's 48 GB partly in use it failed. An idea: when free RAM is short, load it memory-mapped instead (slower first reply, but it loads), or say before loading how much RAM it needs.
3. **The "Can't reach FX Workspace's server" case wasn't reproduced.** The page said it because the server process was gone or restarting; the logs don't say why it went. The desktop app now starts it again by itself, but a crash log (Python's faulthandler to data/logs) would catch a hard crash next time.
4. **Repeated UnicodeDecodeError in server.log** ("'utf-8' codec can't decode byte 0xfa/0xf8" in subprocess reader threads, about 6 a minute): a command whose output isn't UTF-8 (likely nvidia-smi or a PowerShell call run with text=True). Harmless but noisy, and the reading it was making is lost. Fix: errors="replace" on that call.
5. **The voice setup message still says "run run.bat once"** (Settings › Voice, when sherpa-onnx is missing). Installed users have no run.bat; it should offer the setup button instead.
6. **A really full GPU never shows "not enough GPU memory".** On this PC the NVIDIA driver moves what doesn't fit into shared system memory, so a model that's too big loads but runs slowly instead of failing. Diagnostics could warn when a loaded model spilled (it already measures spilled_mb) and offer Run on RAM too there.
7. **test_bonsai doesn't exit by itself** when run with the rest of the suite: its real llama-servers keep the process alive and one stayed on port 8090 afterwards. It could stop what it started in tearDown.
