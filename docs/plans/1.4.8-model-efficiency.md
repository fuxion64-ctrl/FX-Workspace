# 1.4.8 - faster, smarter local models: send only what a turn needs (plan, 10 Nov 2026)

Nothing here is built yet except the measuring script `tools/prompt_inventory.py`. The owner's ask: "only load things when
needed" - a chat that has nothing to do with Roblox carries no Roblox rules, tools or mentions, and the same for every
other heavy area.

## How the numbers were taken

- `.venv\Scripts\python.exe tools\prompt_inventory.py [--ctx 16384] [--tools]` builds the real request for seven kinds of turn through the app's own code (classify_turn, _begin_composer_tools, build_messages, tools_for_current_turn).
- No model, no network, default settings. Tokens are the app's own estimate (3.6 characters a token), not a tokenizer count.
- This folder's data has no identity file and no memories, so those two show 0. On the owner's data they add tokens to every turn; the script must not read the installed app, so that number is for the later measuring session.
- MCP servers were not connected. Roblox's Studio MCP adds about 12,000 tokens when it is (comment in tools/schemas.py, 29 Sep).

## Answers, with numbers

**Sent on every turn that only some turns need**
- The live machine state (244 tokens) goes on every turn, a greeting included: local time, focused window, the titles of every open window, "call list_elements before act_element", "call inspect_screen before any coordinate-based action", "call set_plan first". A greeting has none of those tools - and the window titles are private text the model doesn't need.
- The WORKING paragraph (589) goes on every turn: files, long files, Roblox Studio, web, sources, browser, batch work. On a greeting none of those tools are offered. "Roblox Studio: You can build and change the user's Roblox place yourself" names no tool, so for_tools never drops it - this is why a greeting carries 2 Roblox mentions.
- A web question is classified "read" and gets 38 look-only tools (3,680 tokens): screen, windows, processes, files, clipboard, notes, reminders, roblox_status. It needs the web group and a few core tools: about 2,600 tokens are for other areas. The voice question gets the same 38.
- "why is the sky blue?" turns Visuals on by itself (auto_tools) and its how-to is 270 tokens in the header.
- The voice header adds about 300 tokens to a voice turn.
- Action turns carry a skills list (250-311 tokens) beside the tools that are already on.

**Said twice**
- Every tool's name is in its schema and again in "AVAILABLE TOOLS THIS TURN: ..." in the last message (59-297 tokens).
- "Never say you are only a text assistant" is in the base prompt, the Roblox line and the mode note of every non-action turn.
- The mode note (about 90 tokens) restates what the tool list already shows ("only tools that look are offered").

**What changes every turn, and where it sits (llama.cpp prompt cache)**
- Qwen-style templates put the tool schemas first, then the system message, then the chat. Anything that changes there makes the model re-read everything after it.
- The live state and the CURRENT REQUEST header change every turn but sit in the last message: correct, after the cached part.
- The tool list changes with the kind of turn, and it comes first. Going from a plain question to a web question shares only 625 of 5,112 tokens; web question to picture shares 12. So mixing kinds of messages in one chat re-reads the whole chat each time the kind changes.
- The system message itself changes between action and other turns (1,432 vs 1,444: for_tools keeps different sentences), when the Studio rules join (+115), when a memory is saved (the memory overview is in it), and when the chat is compressed.

**Model calls before the reply (default settings)**
- The message check (chat_guard): one model call for every message of 12+ characters that isn't a greeting. It has its own system prompt; on a one-slot router it may push the chat out of the cache (audit 2.3 - measure first).
- Prompt Prep "Clarify" (the default) is rules only - no model call.
- Planner: a model call at High and above, and at Normal for complex requests. Reviewer: a model call at High and above, and at Normal after an action that changed something. Short or trivial requests skip both.
- So a simple question is 2 calls (check + reply); a PC action at High is 4 or more (check, plan, steps, review).

**How tool results go back to the model**
- Each result is wrapped in two marker lines (about 20 tokens) marking it as data; light.
- After an approved batch the app adds an observation with what changed on the machine.
- Older tool output is trimmed only when the chat is over budget (history.fit); there is no per-result size cap at the loop level - each tool caps its own output. Not measured further here.
- The user sees each step as an Activity row (describe_tool) and the model's own note; no change proposed.

**Instructions a small model can't use**
- "call list_elements", "call inspect_screen", "call set_plan first" on turns where those tools aren't offered (live state block).
- File, browser and Roblox rules on a greeting or a web question.
- Skills it could load (skills list) on top of a 45-61 tool list.

## Changes, in order of what they save

Each: what changes - saving - risk to tool calls - how to measure afterwards (a later session, real models, llama-server's own prompt_n / cache_n timings and wall time).

1. **Message check only when a cheap pre-filter finds something** (audit 2.3).
   - Saves one model call on almost every message, and possibly a full re-read of the chat after it.
   - Risk: safety, not tool calls - fewer messages reach the model check. The rules would decide the rest.
   - Measure: prompt tokens processed by the main call with the check on/off on a 10-turn chat; wall time per reply.
   - **Owner's decision** (it changes what the chat limits look at).
2. **Look-only turns get only the areas they need** (skills.filter_tools on "read" turns, as action turns already have).
   - Saves about 2,600 tokens on a web or voice question (5,781 -> about 3,200); smaller lists also keep the start the same between questions.
   - Risk: a PC question that the classifier doesn't see as one loses its tool for that turn; use_tools can still add it.
   - Measure: tool-call validity on the benchmark set and the 18 search questions (paced, never in bursts), plus "what's using my PC?"-type questions.
   - Safe to build.
3. **Live machine state only when PC tools are offered**, and its tool hints only for tools that are there.
   - Saves 244 tokens on greetings, questions and web turns; stops sending window titles when nothing needs them.
   - Risk: low; turns without PC tools can't act on it anyway.
   - Measure: wall time on greeting/question; check a PC action still sees the state.
   - Safe to build.
4. **WORKING rules by area**: the Files, Long files, Roblox Studio, Web, Sources and Browser lines only when a tool of that area is offered (the Roblox line also needs the bridge or Studio MCP).
   - Saves about 150-300 tokens on non-action turns; no Roblox mention outside Roblox turns.
   - Risk: the system message differs more between kinds of turn - but it already differs today, and the tool list before it differs anyway.
   - Measure: prompt tokens re-read when switching kinds; Roblox turns' behaviour unchanged (studio tests + one live build).
   - Safe to build.
5. **Drop the tool-name line** ("AVAILABLE TOOLS THIS TURN") - the schemas already list them.
   - Saves 59-297 tokens a turn.
   - Risk: it was added because small models used made-up names; may lower call validity on 4B models.
   - Measure: tool-call validity per model with and without it (benchmark).
   - **Owner's decision** after the measurement.
6. **Shorter turn notes**: mode note (about 90), Visuals how-to (270), voice header (about 300) cut to what changes behaviour.
   - Saves 100-500 tokens on the turns that carry them.
   - Risk: low for the mode note; Visuals and voice wording affects reply format - check replies by eye.
   - Measure: a handful of explain / voice replies before and after.
   - Safe to build (text only).
7. **A stable tool-list start for every non-action turn**: greeting, question, web and voice share the same first tools in the same order, extras after.
   - Saves re-reading: today question -> web shares 625 of 5,112 tokens; could share most of the core.
   - Risk: none to calls; order only.
   - Measure: cache_n on a chat that alternates question / web / greeting.
   - Safe to build; worth it only if item 2 lands (smaller lists).
8. **Memory overview out of the system message** (into the last message, or refreshed only at chat start).
   - Saves: a full re-read of the chat each time a memory is saved mid-chat (the system message changes).
   - Risk: the model may weigh it less at the end; low.
   - Measure: cache_n on the turn after a memory save.
   - **Owner's decision** (where memory belongs in the prompt).
9. **Skills list only when no tools for the request were found** (action turns already get the right skills on).
   - Saves 250-311 tokens on action turns.
   - Risk: a request that needs a second skill mid-task can't find it - load_skill still works by name.
   - Measure: multi-area action tasks (files + web) still finish.
   - Safe to build, measure after.
10. **(1.5.0 research A2) One-call path for common PC looks** - the app runs the read tool first and the model only writes the answer.
    - Saves about half the time on those questions (estimate in the research notes, 14 s PC question on Ornith).
    - Risk: wrong tool chosen by rules; needs a fallback to the normal loop.
    - **Owner's decision** (a new path).
11. **(A1) llama.cpp's draft-free speculative decoding** (`--spec-type ngram-*`) through Tune speed, kept per model only if writing gets faster.
    - Saves time on edits that copy most of a file; no tokens saved.
    - Risk: none to calls; flag names differ per build.
    - Measure: Tune speed's own timing.
    - Safe to try in Tune speed.
12. **(A5) A "what it cost" line per reply**: tokens read vs reused, from llama-server's timings. Build this first - every item above is measured with it.
    - Saves nothing by itself.
    - Safe to build.

## Suggested order

- First: 12 (the cost line), then 3, 4, 6 and 2 together (text and tool-list changes, safe), measure.
- Then 7 and 9, measure.
- Owner decides 1, 5, 8 and 10 with the numbers in hand.

## Not verified

- No real model was used: every number is the app's own token estimate, not llama.cpp's count or wall time.
- Identity and memory were empty here; MCP not connected.
- Whether the message check actually evicts the chat from llama.cpp's cache is unmeasured (audit 2.3).
