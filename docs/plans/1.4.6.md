The last patch before 1.5.0 adds features: make what exists work, feel finished and be simpler to use. Five work
stages and a release, each with a stop for your review. Nothing is built until you approve this.

Effort: **High** for the stages that are clear fixes, **xhigh** for the three that need measuring or design
judgement (tools, the design review, building the design).

Where it comes from: your list and clarifications (3 Nov, with screenshots), and the outside audit of 31 Oct - each

## Stage 1 - fix what's broken (High)

**1.1 Renaming a chat does nothing.** Cause found: it uses `prompt()` (index.html:19856), which the desktop app
doesn't have. Fix: the title becomes a text box in place - in the sidebar row, the chat menu and the top bar; Enter
saves, Esc cancels.

**1.2 The mouse's Back button leaves the app on "loading" until the server is restarted.** Likely cause (confirmed
live first): the window opens `splash.html`, then the app, so Back returns to the splash, which waits for a "server
ready" that already happened. Fix: the window ignores Back/Forward (mouse buttons, Alt+Left/Right) and forgets its
history once the app is up; in the app, the Back button closes whatever is on top (a viewer, a panel, a menu). A
splash that finds the server already running goes straight on.

**1.3 System panel: "Unavailable" GPU rows, CPU 0.0%.** The GPU reader works on its own (it read the RTX 3060 Ti at
35% load just now), so the panel's reading freezes somewhere above it. Suspects: nvidia-smi slower than its 3 s
limit while the GPU is busy (the last reading is dropped after 15 s), a first CPU reading (always 0.0), and the
Bonsai engine's separate llama-server. Repro with Bonsai on the dev server, then fix. Done when: under a busy GPU the
panel keeps real numbers, and says "updating" rather than "Unavailable" while a GPU is there.

**1.4 One animation at a time.** In a Deep research turn the same mark moves in three places at once: the Thinking
row, the tool-call drop-down and the research panel. That breaks the app's own rule (one moving signal). Fix: the
Thinking row keeps the moving mark; the drop-down and the research panel show the same state still (a dot, a count,
"reading 6 of 18"). The same check for every other kind of turn (search, image, code, voice). Done when: during any
turn, in every look, one thing moves - checked live (`document.getAnimations()` on screen) and by a test.

**1.5 Harmless chats get locked** (audit 1.1-1.3, confirmed in `chat/chat_guard.py`):
- the checker's answer is read from its *first* category word, so "Is this MALWARE? No - ALLOW" counts as malware.
  Fix: read the final verdict only, and ask for one word;
- the chat borrows the image filter's word lists, where "explicit" counts as sexual and "minor", "child" or "kid" as
  a minor - "a **minor** bug, make the return **explicit**" closes a chat for good. Fix: the chat gets its own
  narrow phrases; a phrase match alone asks the model check instead of closing; only a confirmed case closes for
  good (and still can't be reopened);
- a locked chat shows a visible **Review and reopen** button instead of the hidden double-click.
Done when: a set of everyday coding and chat messages never locks, and the existing harmful set still always does.

**1.6 A local model's extra tool calls disappear** (audit 2.1, confirmed): asked for three tools at once, it gets
the first and the others vanish without a word, so the model thinks they ran. Fix: each one held back gets the
answer "not run yet - call it again if you still need it".

**1.7 Context squeezed too late** (audit 2.3, confirmed): at 97% full a long reply can hit the end first. The
default becomes 90%.

**1.8 Expand repeats the main subject** (1.4.5's known issue): with no prompt, the new area is described as the
surroundings, not with the subject's own words.

**1.9 Small:** a stale screenshot test, tests that expect an E: drive, and the phone/PC flag (audit 7.1: a phone
message running alongside a PC one can swap which tools are allowed - proven with a test first, then carried with
the turn instead of in shared state).

## Stage 2 - tools: faster, and on by themselves (xhigh)

Tools already turn on by themselves (`auto_tools.py`) and the tool list is already cut per kind of turn, so this
stage measures first and changes what the numbers point at.

**2.1 Measure** on Qwen 3.5 4B, Ornith 9B and Bonsai, in the real app: tool tokens per kind of turn, time to the
first word, whole reply time, and how often a reply needs a retry. These are the "before" numbers.

**2.2 Don't re-read the same start.** Tools and fixed instructions go first and stay identical between turns, with
what changes last, so llama-server reuses what it already read instead of reading 2,000+ tokens again. Kept only if
measured faster.

**2.3 On by themselves, more often - and asking where it matters:**
- picture requests turn Image on, "explain / show me how" turns Visuals on, numbers turn Charts on (extended and
  tested on real messages);
- **web search turns on by itself** when a question needs current facts or a source (decided 3 Nov);
- **PC control and app control** turn on for requests about the PC or an app, with safety levels: what it may do
  without asking (open an app, read the screen, read a window's text) and what always asks first (typing or
  clicking in another app, closing things, anything that deletes, sends or buys).

**2.4 Fewer retries:** when a small model writes "I saved the file" without calling the tool, the app asks it again
(up to 3 full re-reads). Try llama.cpp's forced tool format for small models; kept if faster and no worse.

**2.5 Tune speed lets chats in** between its measurements instead of holding the model for 10-20 minutes.

Done when: the before/after numbers are in, and each change that stayed made a measured difference.

## Stage 3 - models: what's really on this PC (High)

**3.1 Images shows the models you have.** Today the Images model list is a fixed catalogue of 9 models
(`media/image_gen.py`); a model file that isn't in it can't be used, and missing ones still appear as choices. New:
the picker lists only what's installed and works. The rest of the catalogue moves to **Get more models**, with size
and what each is good at.

**3.2 Add an image model yourself:** pick a file (.safetensors / .gguf) or a folder, or paste a Hugging Face or
Civitai link. The app works out the kind from the file itself (SD 1.5, SDXL, SD3, FLUX, Z-Image...), uses sound
settings for that kind (steps, guidance, sampler, best sizes), checks the engine can run it, and makes a test
picture before it joins the list. You can rename it, change its settings or remove it from the list (the file stays
where it is). A file the engine can't run says why, plainly.

**3.3 Faster model downloads, like FDM** (chat and image models):
- the file comes down in parts at once - 4 connections, at most 8 - joined at the end, through `netlayer` like
  everything else;
- resume after a pause, a crash or a lost connection, from where each part stopped;
- one download queue with pause / resume / cancel, speed and time left;
- size and SHA-256 checked as today; saved straight to the model drive, free space checked before starting.
Done when: one file with 1 connection against 4 and 8 on this line (numbers in the notes); a pulled cable resumes;
the Tor route still works.

## Stage 4 - design review: decide before building (xhigh)

The aim: an app that's simpler to use, where each thing is in one place and works well by default, instead of many
options that are each "okay". Nothing in the app changes in this stage; it ends with your approvals.

**4.1 unslop audit.** Install unslop ([heydamir/unslop](https://github.com/heydamir/unslop), a Claude Code skill,
read through first - it's third-party) and run it on the real app on the dev server, every look, light and dark.
It looks for clutter: stray gradients and glows, emoji labels, loud copy, uneven spacing, crowded layouts. The
Claude, ChatGPT, Grok and Gemini looks are judged by how closely they match the real apps, so there it only flags
where a look has drifted from its app.

**4.2 A walk-through as a user.** The everyday jobs, start to finish, as someone who doesn't know how the app is
built: first start, a normal chat, Deep research, make a picture, add a model, hide your IP when searching, use it
from the phone, find a setting. For each one: how many screens and clicks, what was unclear, what showed the same
thing twice, which choices didn't need to be choices.

**4.3 Settings, redrawn around what you want to do.** The rules:
- **one place per thing** - a setting lives once (today Tor is in five places on one page, and web search is on two
  pages);
- **say what it does for you, not how it works** - a choice is named by its result;
- **a good default instead of a choice** - where two options are both fine, keep the better one as the behaviour;
- **show an option when it matters** - not a "More options" dump: e.g. Tor bridges appear when Tor can't connect;
- **tools aren't settings** - leak test, speed test and "show my IP" go to Diagnostics.

The Tor example, today: an app-wide route (with Tor), a "Search through Tor" switch, "Which Tor", "Tor port", and a
route per part (search / models / other, each with Tor). Proposed: one row, **Hide my IP**: *Off* · *When searching*
· *For everything* · *Through my own proxy* - the built-in Tor, its status beside it, New identity as a button; a
Tor you run yourself is found automatically; bridges show only when Tor is blocked. Five places become one.

A first map, to be finished in this stage: from 16 pages to about 9 - Appearance; Models (chat, image and voice
models); Assistant (how it works, tools it turns on, proactive help, skills, permissions); Memory (memory, profile,
your files); Web and privacy (web search, Hide my IP, VPN, privacy); Connections (connectors, MCP, Discord, Slack,
phone access); Data and files; Diagnostics; About.

Delivered as a table for you: every setting, **keep / merge / remove**, and for each removal which behaviour stays.

**4.4 Previews with /design.** Each changed screen as a before/after made with /design, from the app's real
screenshots and its real CSS and colours - not a redraw - so the "after" is what you'd get. In it:
- the redrawn Settings pages;
- the message bar with tools on (your ChatGPT screenshot: the chips' rounding, height and inset don't match the
  bar's) - measured against ChatGPT's own bar, then the same in every look;
- **a "Creating image" animation for each appearance** - its own design per look, not one dot grid for all
  (your screenshot is the starting point for ChatGPT's), driven by the real step count, with its percent;
- the subtle glow, after MossadGPT's temporary-chat icon box, in the dark looks where it fits (still, never
  pulsing);
- each look's finished thinking mark (see 5.3);
- whatever 4.1 and 4.2 turn up.
You approve or drop each one. Only approved changes are built.

## Stage 5 - build the approved design (xhigh)

**5.1 Settings** as approved in 4.3. A removed setting's saved value is ignored without errors; its behaviour
becomes the default. Settings search still finds everything.

**5.2 Progress, not raw work.** The per-look "Creating image" animations (from 4.4), on real progress. While a reply
streams, charts, canvas pages and html/svg blocks show a "Building a chart…" card instead of raw code (widgets
already wait this way), with the code behind "Show the code" afterwards. Video and music checked the same way.

**5.3 Thinking animations, finished in every look** - for each kind of work (thinking, reading, searching, a tool,
writing, drawing, waiting), light and dark, with Motion off still showing the state. Then the Orbs / Legacy choice
goes: each look has one finished mark.

**5.4 The message bar, the glow and the rest of the approved changes.**

**5.5 MossadGPT's globe:**
- *Doesn't switch to world view:* a world_monitor result only turns the background globe, which stays fully zoomed
  out, so it looks like nothing happened. Fix: the first world_monitor call of a reply opens the Ops view (unless
  you closed it during that reply).
- *Lock-on doesn't always work:* the reticle only attaches when that aircraft's or satellite's feed is already
  loaded and the item is in it at that moment; a data refresh can leave it on an old copy that stops moving. Fix:
  load the feed when needed, find the item again by id after every refresh, and say "not in the feed right now"
  when it isn't there.

**5.6 Unslop, tab by tab** (asked 4 Nov): every place in the sidebar (Home, Images, Videos, Music, Projects,
Routines, Notes, Docs, Mail, Compare, Browser) and every Settings page gets its own unslop pass - a before/after on
the /design canvas at 1600x900 from the real app, approved before it is built.

Done when: the appearance audit shows 0 issues; the motion check passes in every look, idle and during a reply; Ops
view and lock-on work live on a real flight; your approved before/afters match the built app.
