# FX Workspace 1.5.0 - the older plans (draft for review)

The plans approved earlier and never built: faster big models, expanding pictures, Fx Labs Phase 3, picture-style
training, and the first phase of the AI video editor. Each stage stops for your review. Effort: **High** for the
stages that are clear engineering, **Max** for the two that are open design (marked). Nothing is built until you
approve this.

**Shipped in 1.4.5 (29 Oct):** stages 1 and 2 (Tune speed; Expand in Images), plus the tests moved into `tests/`.
Outpainting notes from the live tests: the engine keeps the masked area (drift 2-3 of 255); strength 1.0 relit the
new area (a visible lighter band), 0.75 doesn't; a wide band given back to the model redrew content at the join, so
the band is 12 px. The 1.5.0 version holds stages 3-6.

## Stage 1 - faster big models (High)

From the Strata video's ideas, already approved:
- **Bigger prefill batches** where they help: a "Fast prompt reading" preset that sets batch / ubatch per model
  (measured before on Qwen3.5-35B-A3B: 2048/2048 read prompts at 966 tokens/s against 393). Applied only where the
  model still fits; measured per model, and shown in Settings › Models.
- **n-cpu-moe auto-tune** for MoE models (Ornith 35B-A3B, Qwen3.5-35B-A3B, DeepSeek-Coder-V2): "Find the best GPU
  split" tries settings - the fewest expert layers on the CPU that still load with room to spare - measures prompt
  and generation speed for each, keeps the fastest in models.ini, and says what it found.
- Checks: before/after tokens a second on each MoE model, no out-of-memory, the reply-time check (real wall time).

## Stage 2 - expand a picture (outpainting) (High)

- In Images, a picture's **Expand**: pick sides (left, right, top, bottom, all) and how much (25 / 50 / 100%); the
  new area is drawn to continue the picture, as a new image (the original stays).
- How: the canvas is enlarged, the old picture placed in it, a mask marks the new area (feathered so there's no
  seam), and the image engine fills only the mask. First: check what stable-diffusion.cpp's server takes for a mask
  (its CLI has --mask); FLUX.2 klein (already an editing model) or an SD 1.5 inpainting pass for the older models.
- Checks: no visible seam on 10 test pictures across models, sizes stay within what each model draws well, VRAM.

## Stage 3 - Fx Labs Phase 3: make a model better at one job (Max)

Pick a job (for example "write Luau for my Roblox game", "answer in my style", "summarise my notes"), and Labs helps
make a model good at it, with proof:
- **Tasks and test cases:** a task is a system message + a set of test cases (input, and how to check the answer:
  must contain, must not contain, matches a pattern, runs as code, or a judge model with a rubric).
- **Baseline:** run the cases on any models you have; a score per case and overall, time and tokens.
- **Variants:** change one thing - the system message, sampling, the quant, a Phase 2 fine-tune - and run again.
- **Compare with a regression check:** what got better, and every case that got *worse*, side by side.
- **Keep the best:** one click makes it the Workspace's model / system message for that task (Port to Workspace,
  already built in Phase 2, for fine-tunes).
- Checks: a sample task end to end, repeated runs agree (variance shown), the judge's own consistency.

**Later in Labs - a built-in model enhancer (asked 4 Nov; research first, nothing built yet).** One place in Labs
that takes a model you have and makes it a better reasoner, without you writing a training script. It would build
on Phase 2's fine-tuning and Phase 3's test runs above. Research to do before it is planned:
- **The AstraGPT modification** ([tantra-ai-labs/astragpt-reasoning-dataset](https://huggingface.co/datasets/tantra-ai-labs/astragpt-reasoning-dataset),
  Apache-2.0, 193,841 records): its reasoning traces show tries, rejected ideas, self-correction and a confidence
  check. Find out what the AstraGPT models themselves changed (training recipe, the "Attempts Blocks" format, any
  verifier or router heads), and which parts fit a small local model.
- **What the enhancer could offer:** a reasoning fine-tune (LoRA) for Qwen 3.5 4B / Ornith 9B from a filtered slice;
  a confidence check the app can read (answer again or say it's unsure); a verifier on hidden states, as the
  dataset's authors suggest. Measure each one with a Phase 3 task, before and after.
- **Limits to check:** VRAM and time on this PC (RTX 3060 Ti, 8 GB), disk (the data and checkpoints go on E:, never
  C:), the traces are model-written and not checked by experts, and each base model's own license.
- **Done when (for the research):** a short write-up in `docs/plans/1.5.0-research.md` with what to build, what to
  skip, and one measured test on a small slice.

## Stage 4 - train a picture style or character (LoRA) (High)

- In Labs: 15-40 pictures of a style or a character -> a LoRA that Images can use ("in my style").
- **SD 1.5 first** (DreamShaper 8, Anything V5 - their full files are already on this PC): fits 8 GB comfortably,
  roughly 20-40 min. **SDXL** (Animagine, Pony) needs a ~7 GB full-size base file the PC has no room for now - it
  comes when there's space.
- Captions written per picture by the vision model (editable), latents cached, 8-bit Adam, gradient checkpointing;
  sample pictures every N steps; the LoRA goes to the image engine's LoRA folder and shows as a choice in Images.
- Checks: a style learned from 20 pictures recognisably, VRAM stays under 8 GB, the LoRA loads in sd-server.

## Stage 5 - the AI video editor, phase 1: a montage cut to the beat (Max)

Its own place, **Editor** (not inside Music - it reads from the music library):
- Pick clips (from Videos or your own files) and a song (from Music or a file), say what you want ("upbeat, fast
  cuts on the chorus").
- The song's beats and sections are found on this PC; each clip is described by the vision model; the assistant
  plans the cut (which clip, which part of it, on which beats); the render goes beat-exact to a video file.
- A preview with the plan as a strip of clips you can re-roll or reorder, then render again.
- Later phases (separate releases, already agreed): 2 an editable timeline, 3 captions and transitions, 4 "make a
  30 s hype edit" from one sentence.
- Checks: cuts land on beats (measured, within a frame), a 60 s montage renders on this PC in reasonable time.

## Stage 5a - design references from real companies, for Claude and for the app's assistant (High)

Asked 4 Nov. Two open collections that describe how well-known products are designed, written for AI agents:
- **[VoltAgent/awesome-design-md](https://github.com/voltagent/awesome-design-md)** (MIT, ~125k stars): 84
  brands (Apple, Google, Stripe, Linear, Vercel, Notion, Airbnb...). Each has one DESIGN.md in the Google Stitch format:
  theme and atmosphere, colour roles, type, components, layout, depth, do's and don'ts, responsive rules, and a
  prompt guide for agents, plus light/dark preview pages.
- **[ihlamury/design-skills](https://github.com/ihlamury/design-skills)** (MIT): 87 Claude skills, one per company,
  with MUST / SHOULD / NEVER rules for colour, type, spacing, states and animation (`npx skills add ihlamury/design-skills`).

**Use 1 - for Claude building FX's looks.** Install the few that match a look we're designing, as project skills in the
workspace's `.claude/skills/`, next to unslop. Each is read in full before it's used.
- Glass: Apple.
- Paper: a publishing or reading product.
- A future Google-like look: Google.
- Rechecking the AI looks: Claude, ChatGPT, Grok and Gemini, if they're there.

The /design boards then cite which rule each choice came from.

**Use 2 - for the app's own assistant.** A "Design like..." choice for /design and Canvas: a page in the spirit of a
named product's design language. How a user meets it:
- They type "/design a pricing page like Stripe", or pick a style from a short list.
- The assistant gets that style's DESIGN.md as its brief.
- Its answer says "in the style of", never "by".
- The files ship in the app (MIT, credited in About and THIRD_PARTY.md). Nothing is fetched per request.

**Rules:**
- **Inspired by, not a copy.** No logos, wordmarks, product names or trademarked fonts in what it makes. San Francisco
  becomes Segoe UI Variable or Inter, and Google Sans becomes a free look-alike. A page must never pass itself off as
  that company's own site.
- **unslop still applies.** Where a file's taste is a known tell (Stripe's purple gradients, glow), unslop wins for
  FX's own screens. For a user's "like Stripe" page, it's their choice.
- Check both repos before 1.5.0: licence still MIT, how current the files are, and quality, spot-checking 5 against
  the real sites.

**Steps:**
1. Pick about 12 references and check them.
2. Write a skill that loads one by name.
3. Add /design "like ...".
4. A /design board comparing the same page in 3 styles, for your approval.

## Stage 5b - a "Glass" appearance: liquid glass and an Apple-like way of designing (xhigh)

Asked 4 Nov. A new look of its own, next to Classic, Eclipse, Aurora, Sunrise and Terminal. It's inspired by
liquid glass and Apple's way of designing, but it isn't a copy of macOS. No Apple names, icons or SF fonts: SF is
only licensed for Apple platforms, so it uses Windows' Segoe UI Variable, or Inter.

**What makes it "Apple-like" (the rules the look follows):**
- **Content first, the interface defers to it.** The chrome is light and thin and gets out of the way. Glass is
  used only on things that float over content: the sidebar, the top bar, the message bar, menus and sheets. Never
  on the content itself (replies, cards, pictures).
- **Depth that means something.** Three layers: content, floating controls, sheets and menus. Each layer is a
  little more frosted and lifted, so you can always tell what is on top.
- **Clarity:** one system font, sizes on a strict scale, generous space, rounded corners that nest (an inner
  radius equals the outer one minus the padding), a single tint colour for actions.
- **Glass that stays readable:** the blur and tint adapt to what's behind them, text keeps 4.5:1 contrast, and a
  "Reduce transparency" switch (plus Windows' own setting) turns glass into solid surfaces.

**Liquid glass, concretely:**
- Surfaces bend the light at their edges: a thin bright rim, a soft inner highlight, and a slight lens effect
  (SVG displacement where the GPU allows it, a plain blur where it doesn't). Light mode and dark mode.
- Controls inside glass (buttons, chips, the model picker) are glass too. A press makes them "pool" slightly, like
  a drop of liquid, instead of just changing colour.

**Animations (the part that makes it feel like Apple):**
- **Springs, not easing curves:** one spring (a fixed stiffness and damping) for everything that moves, so the
  motion feels physical. It stops without bouncing for small moves and with one soft overshoot for sheets.
- **Things grow from where they came from:** a menu opens out of its button, Settings opens as a sheet, and a
  picture zooms out of its thumbnail. Closing runs the same path back.
- **Interruptible:** clicking again mid-animation turns it around from where it is; nothing waits for an
  animation to finish.
- **The glass morphs:** when the message bar grows or a chip turns into a menu, the glass shape stretches into its
  new form instead of fading out and back in.
- **The thinking mark for Glass:** a small liquid drop that slowly changes shape while it thinks, splits for
  tools, and settles back into one drop when the reply starts. It's one moving signal, as the app's motion rule
  says.
- "Reduce motion" (Windows' setting and Motion off) turns springs into short fades.

**How a user meets it:** Settings › Appearance › Glass, with a live preview as it's picked (light / dark / follow
Windows). On a weak GPU, or with Windows' "transparency effects" off, it shows a note and draws solid glass instead,
so it never stutters. The assistant's `app_appearance` tool can switch to it ("make it look like glass").

**Steps:** 1 a /design board at 1600×900 with Home, a chat, Settings and a menu in light and dark, and the motion
as a playable board, for your approval; 2 build it as `data-skin="glass"`; 3 check it: 60 fps on this PC while
scrolling and typing (measured), contrast in every state, Reduce transparency and Reduce motion work, and
nothing from Glass leaks into the other looks.

**Note:** unslop counts glass and blur as signs of a generated look. Here they're the look's whole idea, the same
as Aurora's sky. So the rule is restraint: glass only on floating chrome, never glowing colour, one tint.

## Stage 5c - a "Paper" appearance (High; 1.5.0 if there's room, else 1.5.1)

Asked 4 Nov. A look like reading and writing on good paper: calm, warm, made for long reading and writing.
- **Material:** warm off-white paper (a faint, still grain - never moving), ink-black text, a dark mode that is
  "paper at night" (warm charcoal, not blue-black). Hairline rules instead of boxes, like a notebook.
- **Type:** a book serif for replies and headings (a free one, e.g. Literata or Source Serif), the interface in a
  quiet sans; generous line height; a narrow reading column.
- **Details:** the message bar is a sheet lying on the page; code blocks are index cards; the sidebar is the margin.
  One ink colour (deep blue or red-brown) for links and the main action.
- **Motion:** pages, not glass - a reply fades in line by line, like ink drying; menus slide out like a tab.
  The thinking mark: a fountain-pen nib writing a small looping line that never repeats exactly, and lifts off when
  the reply starts. One moving signal; Reduce motion shows a still nib.
- **How a user meets it:** Settings > Appearance > Paper, with a live preview; the assistant's appearance tool knows it.
- Steps as for Glass: a /design board at 1600x900 first, then build it as `data-skin="paper"`, check contrast,
  print (it should print well) and Reduce motion.

## Stage 5d - faster and better pictures (High; asked for 4 Nov)

Already on in 1.4.6: flash attention (`--diffusion-fa`), the step cache for the models it doesn't harm, a warm
engine between pictures, eager loading. What's left needs measuring on this GPU (RTX 3060 Ti, 8 GB), model by model,
with the same prompts and seeds, before/after in the notes:
- **Faster:** a quantised copy (Q8 / Q5) of each big model where the engine supports it - less to move per step on
  8 GB; skip `--vae-tiling` when the picture fits in VRAM (tiling costs time); TAESD as a fast preview decoder so the
  card can show the real picture forming instead of only the animation; keep the text encoder loaded between pictures.
- **Better:** a light upscale pass (2x, an ESRGAN-type model) as an option for "Best"; per-model sampler and step
  defaults checked against each model's own card; a negative prompt per family (SD 1.5 / SDXL / Pony) by default;
  "Improve my prompt" on by default for short requests.
- Done when: each change has its number (seconds per picture, and a side-by-side), and nothing got worse.
