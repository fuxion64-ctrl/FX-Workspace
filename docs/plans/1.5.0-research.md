# 1.5.0 - research notes (4 Nov 2026, nothing built)

Two lists: what could go into the app, and what would make Claude better at working on it. Web sources are mostly
blogs and doc mirrors; each item says what still needs checking.

## A. What the app could add

1. **Faster replies when it edits text or code: llama.cpp's draft-free speculative decoding.** `--spec-type
   ngram-simple` / `ngram-mod` reuses token runs already in the chat as guesses, with no second model and no extra VRAM.
   The docs name "rewriting source code" as the case it fits: edits that copy most of a file. How a user would meet
   it: nothing to set; Tune speed tries it per model and keeps it only if writing gets faster. Check first: flag
   names differ between llama.cpp builds (`--draft-max` vs `--spec-draft-n-max`), so it needs to be detected per build.
2. **Fewer model calls per turn.** Measured in stage 2: a tool turn is 3-6 model calls (the classifier, plan, 2-3
   steps, review). The biggest remaining cost is the PC question taking 4 steps on Ornith (14 s). Idea: a "one call"
   path for the common looks (processes, files, windows): the app runs the read tool first, from the classifier, and
   the model only writes the answer. Expected: about half the time on those questions. Measure the same way as stage 2.
3. **Your models from your phone, private** - LM Studio's LM Link (over Tailscale) and its phone app show people
   want this. FX already has Phone access; the gap is reaching it away from home without opening a port. Idea: an
   optional Tailscale/WireGuard route in Settings > Phone access, with the same sign-in.
4. **MCP everywhere** - Jan ships MCP and browser automation, and Open WebUI has team features (roles, SSO). FX has
   MCP; worth adding: a short list of checked servers to add in one click, and per-server permissions shown on the
   approval card (which server, which tool).
5. **A "what did it cost" view per reply** - the stage 2 proxy showed what the app doesn't: tokens read vs reused,
   per call. A small line in Activity ("read 628 new tokens, reused 3,202") would show users and us when a chat gets
   slow because its start keeps changing.
6. **Labs: the model enhancer** (already in the 1.5.0 plan) - the AstraGPT traces and a Phase 3 task to prove it.

## B. What would make Claude better at this work

1. **A turn bench in the repo** (`tools/turn_bench.py`, from stage 2's `measure.py` and `tapproxy.py`). It runs a list of
   real messages against the dev server and real models, reports wall time, calls and tokens read/reused, and declines
   approvals. Today every measurement starts from scratch; with it, "measure, don't guess" takes one command, and
   before/after numbers come out the same way every time.
2. **A dev-only switch so approvals never go to a desktop popup** (for example `AGENTIC_APPROVALS=web`). In stage 2 a
   test turn opened a native popup twice; Stop didn't close it, and it took a server restart to clear (see
   1.4.6-suggestions.md).
3. **The capture pipeline in the repo** (`tools/capture.py`: headless Chrome at 1600x900, with a look and scheme per
   shot). It now lives in a temporary folder and gets rebuilt; checked in, every UI change can come with before/after
   pictures straight away.
4. **Git on PATH** (or a `tools\git.cmd` wrapper pointing at GitHub Desktop's git). Every commit needs the long path today.
5. **A hook that copies index.html to static/** after an edit to it (Claude Code hooks): forgetting that copy is the
   most common way to test stale UI.
6. **A dev data reset** (`tools/dev_reset.py`): one command for a clean, known dev settings file (Auto effort, no per-model
   pins, Classic light). Stage 2 found the dev data pins Qwen to High and Ornith to Balanced. That changes what gets
   measured, and it took a while to see.
7. **Playwright MCP or the browser pane for UI checks**, as the guides recommend: Chrome's extension is often
   unreachable here, while the built-in browser pane and headless Chrome both worked.

## C. The two you asked to look into (from the 1.4.6 plan)

- **AstraGPT reasoning dataset** ([tantra-ai-labs/astragpt-reasoning-dataset](https://huggingface.co/datasets/tantra-ai-labs/astragpt-reasoning-dataset), Apache-2.0): 193,841 English instruction / reasoning / answer records (JSONL and Parquet). Each reasoning starts with "Attempts Blocks" in think tags: tries, rejected approaches, self-correction and a confidence check. Model-written and machine-curated, not checked by experts, and not meant as a factuality benchmark. Its authors name fine-tuning, verifier heads on hidden states and calibration as uses. For FX: the Labs model enhancer (1.5.0 plan, stage 3) - a reasoning LoRA for Qwen 3.5 4B / Ornith 9B from a filtered slice, measured with a Phase 3 task before and after; its trace format for Labs' own data.
- **DeepSeek Harness** ([deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness), MIT, a developer preview; sources mostly secondary): an agent framework where everything is a plugin - models, tools, the agent loop, sessions, sandbox, UI. Worth comparing with FX's loop before 1.5.0: its tool-plugin boundary (FX registers tools in three places: schemas, dispatch, skills) and its session model. Read the architecture docs first; nothing to take over blind.
