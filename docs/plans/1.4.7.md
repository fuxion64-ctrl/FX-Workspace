# FX Workspace 1.4.7 - reliability (4-5 Nov 2026)

A fix release after 1.4.6 (the UI/UX polish, commit 41bcb22): every technical bug and reliability problem the owner hit, fixed and tested. Release notes: docs/releases/1.4.7.md; off-plan ideas: docs/plans/1.4.7-suggestions.md.

The core runtime: model loads, llama-server, the picture flow and ports. Each reported failure was reproduced (or
its cause read from the installed app's own logs, read-only), fixed, and covered by a test. Live runs used the dev
server (port 8010, launch config `fx-rel`: its own models.ini in a temp folder, router on 8190) with real models
from `E:\ClankerLocalCpp\Clankers` - never the installed app or its data. Tests: `tests/test_reliability_146.py`
(38) plus the updated older ones; the full suite (without test_bonsai) passes.

## Found while testing (fixed)
- **A hung router made helper calls wait 120 s each.** Prompt prep and the planner trusted a 20 s "it's up" cache, so
  against a router that accepts connections but doesn't answer, "hi" took **329 s**. They now check fresh and recover
  first: **32 s** (the model load included).
- **One message bigger than the window broke the chat for good.** After a 166,000-character paste to a 16k model,
  even "Say hi" was "too long" (47,814 tokens). The message is now left out with a note ("Attach it as a file instead")
  and the next message answered in 6.4 s.
- `force_load` dropped the router's own words ("failed to load"), so Settings' Load button couldn't be diagnosed.
- The agent's browser refused to start when another browser held its control port; it now moves (still never reuses
  or closes a browser it doesn't own).
- The test suite started a real llama-server when it reached the new recovery path (`tests/__init__.py` turns
  auto-start off; the recovery tests turn it back on with mocks).

## Checked, no change needed
- Stop mid-reply: stops at once ("Stopped" at 9.0 s, the moment it was pressed), next message 2.7 s.
- The GPU passing between the image engine and the chat model: chat right after an image 21.4 s, no deadlock.
- A tool that hangs: every tool already runs with a hard timeout and says so (`pc/tool_executor.py`).

## Not verified live
- Network off (the kill switch and search fallbacks have their own tests; switching this PC's network off would cut
  the session).
- The desktop app's server restart (`watchServer` in desktop/main.js) - built and in the installer, not crash-tested
  in the real window.
- A real CUDA out-of-memory: on this PC the NVIDIA driver spills into shared memory instead (a 7B at 131k context
  with ngl 99 loaded and answered), so the "not enough GPU memory" card was tested from the log text only.

## Approved suggestions, built (5 Nov)
- **Missing files in the picker.** A model whose GGUF (or image projector) is gone shows "file missing" with **Find**
  (looks for the same file in the model folders, the older install folders and beside the other models' files - 0.1 s
  here - and points the entry at it) and **Remove** (the models.ini entry only, with a backup; a missing projector is
  dropped instead so the model keeps reading text). Auto never picks such a model. Checked live: Gemma-4-E4B-Tools was
  marked, Find said it isn't on this PC, Remove took it off the list.
- **Short of RAM, load from disk.** A model set to read itself into RAM up front (load-mode = none) that can't reserve
  the RAM loads memory-mapped instead - once, with a note in the chat; the next failure says why.
- **crash.log.** faulthandler writes every thread's stack to data/logs/crash.log on a hard crash.
- **No more decode errors.** Text output of every command the app runs has odd characters replaced (the desktop app
  runs Python in UTF-8 mode; Windows tools answer in the console's code page).
- **Missing packages repaired at start.** The launcher installs requirements.txt again when one of the app's key
  packages (sherpa-onnx, uvicorn, fastapi, httpx, psutil) is missing, not only when the file changed; the voice page
  says to restart instead of "run run.bat once".
- **A spilled model is offered the split.** The first time a model overflows into shared memory (over 512 MB), a note
  offers Run on RAM too.
- **test_bonsai is safe.** Its load test called force_load, which really restarted the running llama-server on
  PrismML's build - that left a router on 8090 and kept the run from exiting. Now patched; the whole suite, test_bonsai
  included, passes in 91 s (1,746 tests).
- Also: the model list follows models.ini at once after an entry is removed (the router only re-reads it at its next start).
