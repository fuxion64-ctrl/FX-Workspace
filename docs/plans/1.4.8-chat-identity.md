# 1.4.8 - the right chat, kept settings, whole chats (plan, 10 Nov 2026)

Plan only - nothing built. Covers audit 2.1 (messages carry no chat id), 3.1 (page settings lost when the port
changes) and 2.8 (long chats lose their start). Line numbers are for `aab92cd` unless marked "now".

## What is true today

**2.1 - one chat for the whole server, and messages don't say which chat they are for**
- `core/state.py:32` - one `app_state` holds one `conversation` and one `active_chat` for every client.
- `core/state.py:93` - `ChatRequest` has no chat id. A message goes into whatever chat the server has open, not the one the page shows.
- `api/server.py` `start_chat` - checks only a temporary chat's id (`req.temporary_chat`); a normal chat is never checked.
- Opening a chat (`/api/chats/{id}/open`, `_with_lock`) swaps the server's chat for every client at once: the main window, the mini window, the phone page and a second window all share it.
- `api/server.py:893-939` `_channel_turn` (Discord, Slack, webhook) opens the channel's chat, releases the lock, then starts the turn - a PC send in that gap lands in the channel's chat. Putting the PC's chat back can time out silently (`:931`); the PC's next message then goes into the channel's chat.
- Per-turn state (`turn_*`, `raw_mode`, `turn_origin`, `current_user_request`) also lives in `app_state`.

**3.1 - page settings live in the browser, per address**
- `index.html` keeps these in localStorage (12 uses): `welcomed`, `toured`, `seenVersion`, `mode`, `textScale`, `motion`, `contrast`, sidebar width and state, `pinned`, `tools`, `preset`, `pendingTurn`; Electron keeps the window zoom per origin.
- Browser storage belongs to one address and port. Since 1.4.7 the app can move from port 8000 to another (`launcher.pyw` `choose_ports`), and then every one of these is gone: the welcome and the tour show again.

**2.8 - long chats lose their start on disk**
- `chat/chat_store.py:35` `MAX_TRANSCRIPT = 400` and `:41` `MAX_CONVERSATION = 300`; `save()` (`:104-107`) keeps only the last 400 transcript entries and 300 conversation messages, so older ones are deleted from the file for good on the next save.
- Nothing tells the user. The model's view is already fitted separately at send time (`history.fit`, `agent/models.trim_conversation`), so the disk cap isn't needed for the model.
- Message actions (edit, retry, branch: `api/server.py` ~`:2627`) point at a transcript entry by its index in the list the page has.

## The smallest safe design

**Chat id on every message (2.1)**
- `ChatRequest.chat_id: str | None` - the id of the chat the page shows; `None` means "a new chat".
- `start_chat` checks it in `turns.start(on_start=...)`, which already runs under the turn manager's lock: the id must equal `active_chat["id"]` (or both are "new"). On a mismatch the message is refused with `{"chat_changed": true, "message": "This chat changed on another screen - reopen it to send."}` and the page reloads the chat list. Nothing is sent to the model; the text stays in the box.
- A temporary chat sends its id the same way; the existing `temporary_chat` check stays as the stricter one.
- Routines and channel turns don't come from a page: they keep running in the chat they open themselves, but `_channel_turn` opens its chat and starts its turn without releasing the lock in between (a `turns.start_locked` variant), and putting the PC's chat back is retried and logged, never silent.
- Later (not this release): move per-turn state into one turn object passed down, so two screens can't mix turn settings. Too wide for 1.4.8.

**Page settings on the server (3.1)**
- `GET/POST /api/ui-state`: a small JSON file `data/ui_state.json` with the keys above, cleaned by a `clean_ui_state` like every setting.
- Two profiles, `pc` and `phone` (from `remote_access.is_remote`): the phone's text size or sidebar must not change the PC's.
- The page reads it at start; localStorage stays as a fast cache. First run after the update: if the server has nothing and the browser has values, the browser's are sent up once (migration).
- `pendingTurn` stays out: the server already reports the running turn in `/api/state`.
- Window zoom: `desktop/main.js` reads it from `/api/ui-state` after it knows the port (Electron's own per-origin zoom is lost the same way).
- Phone access: `/api/ui-state` goes in `remote_access.PHONE_ALLOWED` (the phone profile only).

**The whole chat on disk (2.8)**
- `chat_store.save()` keeps every transcript entry and every conversation message; the 400/300 caps go.
- The page gets the last 200 entries with the chat and asks for older ones as you scroll up: `GET /api/chats/{id}/transcript?before=<index>&limit=200`.
- Each entry keeps its absolute index (the open payload carries `offset`), so edit / retry / branch keep pointing at the right message.
- The model still gets only what fits (`history.fit`), unchanged.
- Size: a chat file is rewritten on every turn. A 2,000-entry chat with tool steps is a few MB; measure save time at 1k / 5k / 10k entries before deciding on an append-only format (not planned now).

## Stages (stop for review after each)

**Stage 1 - chat id on every message** (server + page)
- Server: `ChatRequest.chat_id`, the check in `start_chat`, the refusal text; `_channel_turn` without the unlocked gap; the PC's chat put back with a retry and a log line.
- Page (`index.html`, the UI session): send `chat_id` with `/api/chat`, handle `chat_changed` (keep the draft, reload the chat list, say so).
- Tests: a message for chat A while B is open is refused and nothing runs; "new chat" with a chat open is refused; a temporary chat still works; a channel turn can't take a PC message (simulated gap); restoring the PC's chat failing is logged.
- Live check (dev server): open chat A in the main window and chat B in a second window or the phone page, send from the first - refused, draft kept; reopen - it sends to A.
- Review stop.

**Stage 2 - page settings on the server**
- Server: `/api/ui-state` (two profiles), the file, cleaning, `PHONE_ALLOWED` entry.
- Page: read at start, write on change (debounced), one-time migration from localStorage. Desktop: zoom from it.
- Tests: profiles kept apart; unknown keys dropped; migration happens once; a bad file falls back to defaults.
- Live check: set text size and the sidebar, run the dev server on another port (8011), open it - the same; the welcome and tour don't show again.
- Review stop.

**Stage 3 - whole chats**
- Server: drop the caps in `save()`; the paging endpoint; `offset` in the open payload; message actions by absolute index.
- Page: load older messages on scroll; actions send absolute indices.
- Tests: a 1,000-entry chat saves and reopens whole; paging returns the right slice; edit on an entry from an older page edits that entry; the model's request is the same size as before for a long chat.
- Measure: save and open time for 1k / 5k / 10k entries on this PC (real disk).
- Live check: a long temporary-free test chat on the dev server, scroll to its start, retry an old message.
- Review stop.

## What could break

- **Old chats**: files already cut to 400/300 stay cut - lost entries can't come back. They open as before.
- **Temporary chats**: never saved, so stage 3 doesn't touch them; stage 1 must keep the existing `temporary_ended` refusal and order of checks.
- **Routines**: they send no chat id - they must not be refused by the new check (they run in the chat the server has open, as today).
- **Channels**: their chat is opened by the server; the new check must not refuse them, and the PC's chat must come back even when the channel turn fails.
- **The phone page**: it shares the server's open chat today, so phone and PC see each other's chat switches; with ids it gets "this chat changed" instead of silently writing into the other chat. It needs the same `chat_changed` handling as the main page.
- **Mini window**: same as a second window - it must send the id of the chat it shows.
- **Message actions** (stage 3): any code that uses a transcript index from the page must use the absolute one.
- **Big chat files** (stage 3): slower saves on very long chats - measured before shipping.
- **Two windows editing ui-state** (stage 2): last write wins per key; fine for settings like these.

- Keep the welcome/tour flags per profile, or once for the whole install?
